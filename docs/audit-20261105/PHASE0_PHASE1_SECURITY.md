## 3. P0-ROLE-001: 이메일 기반 관리자 추정

위치: Worker의 `loadUserFromD1` 및 `syncFromD1` 사용자 복원. 기존 코드는 `row.email.includes('admin')`로 관리자 역할을 부여했다.

원인: 자가 가입 이메일을 검증된 권한 부여로 오인. 가입 직후 user이더라도 새 isolate/재시작 시 관리자 역할로 바뀔 수 있다. 과거 세션의 role 또는 메모리 캐시만 읽으면 권한 철회도 즉시 반영되지 않는다.

재현: 실제 SQLite를 사용하는 Node 격리 어댑터에서 **이전 두 추정식과 기존 재검증 부재를 복원한 코드**로 일반 가입→새 모듈/isolate→관리 API 접근 허용 200을 재현했다. 과거 배포 전체를 재실행한 것이 아니라 해당 결함 동작의 격리 재현이다. **운영 공격·운영 악용 흔적 조사·운영 계정 변경은 하지 않았다.**

수정:

- 이메일 기반 추정식을 제거했다.
- D1이 바인딩된 환경은 승인 기록이 있는 `luno_user_roles`만 역할 근거로 사용한다.
- user/admin/partner/developer/creator/ads만 허용하며, 미등록/알 수 없는 역할/역할 테이블 미설치 시 user로 제한한다. 테이블 없음 이외 DB 오류는 무시하지 않는다.
- 세션 발급 및 매 인증 요청에서 역할을 다시 읽는다. 캐시된 관리자나 세션 행의 과거 role로 승격하지 않는다.
- 비파괴·중복 실행 가능한 **로컬 준비 마이그레이션**을 작성했다. 역할 테이블을 런타임에 자동 생성하거나 관리자에게 자동 권한을 부여하지 않는다.

이 역할 테이블은 LN5 users.role 목표와 대조할 **보안 격리용 이행 설계안**이다. PHASE 2에서 최종 역할/조직 멤버십 모델과 통합한다. 이 수정만으로 전 콘솔 RBAC 완료가 되지는 않는다.

### P0-SCOPE-002 추가 수정

개발자 앱 생성 시 owner_id를 기록하고 목록은 소유자(또는 관리자 조회) 범위로 제한했다. 비밀키 원문은 생성 응답에서 한 번만 전달하고 Map에는 해시만 보관하며, 목록에는 원문과 해시 모두 반환하지 않는다. 타 소유자의 Webhook 설정 요청은 403, 없는 앱은 404로 거부한다. 실제 지속 저장이 없는 Webhook 설정은 active=true의 가짜 성공 대신 503을 반환한다.

[실제 HTTP 앱 격리 증거](./phase1-app-http.json): 새 계정 두 개로 앱 생성→소유자/비소유자 조회→Webhook 변경 권한을 검사했다. 이 검사는 앱의 지속 저장·실제 API 키 인증·공급자 전송·조직 멤버십까지 완성했다는 뜻이 아니다. 현재 앱 등록의 역할/조직 자격 정책은 LN5 S5와 추가 대조해야 한다.

로컬 Worker는 운영과 다른 이름·database_id·저장 경로를 사용했다. users/friends/wallets 등 초기 SQL은 새 로컬 D1에만 적용했다. 실제 재시작 HTTP 검사는 역할 테이블이 없는 안전 기본값도 확인했다. 명시적 grant·철회 검사는 SQLite 어댑터에서 실행했으며 Cloudflare 운영 DB에서 실행하지 않았다.

## 5. 배포 영향: 지금 자동 적용하면 안 되는 이유

운영 users에 역할 컬럼이 없고, 승인된 역할 할당도 확보하지 못한 상태다. 수정본을 그대로 배포하면 기존 이메일/seed 추정 관리자도 user로 제한되어 관리자 접근이 중단될 수 있다. 이는 의도된 fail-closed 동작이지만 운영 도입에는 다음 순서가 필요하다.

1. 전체 P0 권한 경계 검사를 계속하고 미해결 중대 결함을 수정한다.
2. 관리자가 될 계정의 **불변 user_id를 운영자가 확인**하고 승인 목록을 준비한다. 이메일 패턴/기존 세션 역할로 자동 선정하지 않는다.
3. 역할 마이그레이션과 명시적 승인 부여에 대한 운영 DB 변경안을 검수한다.
4. 비관리자 승격 거부·승인 관리자 접근·철회·기존 세션 처리·장애/롤백을 스테이징에서 확인한다.
5. 변경/영향을 제출하고 PO의 별도 운영 DB·배포 승인을 받은 뒤 적용한다.

롤백은 역할 테이블/감사 필드를 보존하고 권한을 안전하게 철회/전진 수정하는 방식으로 한다. **이메일 추정 취약 코드로 되돌리지 않는다.** namespace와 기존 마이그레이션 이력은 삭제하지 않는다.

## 7. PHASE 0부터 병행한 디자인 조사

- 6개 앱 모두 shared/design-v2.css를 가져오지만 USER는 추가 토큰/테마 CSS 7개 계층도 중첩한다. 동일 브랜드 토큰이 존재해도 모든 실제 컴포넌트가 이를 따르는 것은 아니다.
- 기존 v2 토큰은 light/dark·spacing·radius·layout을 제공한다. 삭제하지 않고 실제 화면 적용률과 고정 색상/크기 충돌을 조사해야 한다.
- 프로필 사진 진입을 포함해 최신 소스를 다시 수집했고, 69개 영역은 페이지 수와 구분한다. 이번에는 인증된 전 역할 화면/전체 디자인 QA를 완료하지 않았다.
- 재설계 방향은 메시지 중심의 USER와 고밀도 작업 중심 콘솔을 같은 semantic token/component 체계로 연결하는 것이다. 목록/상세, 폼, 테이블, 모달, 알림, 오류/빈 상태·권한 없음 상태부터 계약을 정리한다.
- 신규 토큰이 필요하면 별도 v3 버전으로 작성하고 v2/LN6 차분을 남긴다. 현재 단계에서는 미완성 기능을 작동하는 새 시안으로 포장하지 않는다.

실제 전면 디자인 구현은 PHASE 11 범위로 추적하되 조사와 구조 설계는 지금부터 병행한다. 이번 보안 수정만으로 디자인 리뉴얼 완료라고 보고하지 않는다.
