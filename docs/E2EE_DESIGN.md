# LUNO E2EE 설계서 (E1)

결정 반영: 마스터 지시서 6-1 + 대표 결정(2026-11-21: 착수 확정,
새 기기에 과거 기록 제공, 보안 검토는 내부만).

## 1. 범위

- 암호화(항상 켜짐, 끄는 스위치 없음): 1:1 채팅, 그룹 채팅(최대 500명),
  나와의 채팅(Keep). 새 메시지는 `ciphertext` 종류로만 전송.
- 평문(화면에 표시): 봇이 멤버인 방(PC 작업실 포함), 공식 계정 방,
  오픈채팅, 피드·스토리·VOOM. 그룹에 봇 초대 시 확인 절차를 거친다.
- 통화: WebRTC DTLS-SRTP 그대로. 보안 코드와 연동하기 전에는 통화를
  "종단 간 암호화"라고 표기하지 않는다.
- 기존 평문 메시지: 그대로 둔다. 각 방에 "이 시점부터 종단 간
  암호화됩니다" 시스템 메시지를 1회 남긴다.
- 구버전 앱: 서버의 앱 최소 버전 미만은 업데이트 안내 후 차단한다.

## 2. 위협 모델

- 서버는 정직하지만 엿볼 수 있고, 유출될 수 있다고 가정한다.
- 서버가 보는 것: 발신자·수신자·방·시각, 기기 목록, 공개키 번들,
  암호문의 존재·크기·개수, 백업 암호문(5장, 복원 문구 없이는 못 읽음).
- 서버가 못 보는 것: E2EE 방의 메시지·첨부 내용, 백업 평문.
- 네트워크 공격자: TLS + 암호문 이중 보호. 분실 기기는 원격 로그아웃·기기
  삭제로 대응하고, 삭제된 기기의 키는 폐기한다.
- 기록 제공(5장)은 순방향 비밀성(forward secrecy)을 약화한다. 백업을 가진
  자는 백업 시점까지의 기록을 읽을 수 있다. 대표 결정에 따른 절충이며,
  외부 검토 전 상태로 표시한다.

## 3. 암호 구성 요소

- 신원키: 기기마다 X25519(합의용) + Ed25519(서명용) 1쌍씩.
- 서명 prekey: X25519, Ed25519 신원키로 서명, 주 1회 교체.
- 일회용 prekey: X25519, 20개씩 보충. 번들 조회 1회에 1개 소진.
- 1:1 세션: X3DH 합의 + Double Ratchet.
  - X3DH: DH(신원A, 서명B) + DH(임시A, 신원B) + DH(임시A, 서명B) +
    DH(임시A, 일회B, 있으면). HKDF-SHA256으로 세션 비밀 도출.
  - Ratchet: 루트·송신·수신 체인(HKDF-SHA256), 메시지 AES-256-GCM.
    v1 헤더(DH 공개키, N, PN)는 평문이다(개수 메타데이터만 노출, 위협
    모델 범위 안). 헤더 암호화는 추후 버전에서 도입한다.
- 그룹: Sender Keys. 발신자마다 체인키 + 서명키를 두고, 메시지를
  체인에서 뽑은 키로 암호화하고 서명한다. sender key는 1:1 세션으로
  암호화해 멤버에게 나눠 준다. 퇴장·내보내기 시 남은 전원이 교체한다.
- 여러 기기: 웹 브라우저 1개 = 기기 1대. 메시지를 상대 전 기기와
  내 다른 기기 각각에 암호화해 보낸다(서버는 기기별 암호문을 보관).
- 금지: 암호 알고리즘 직접 구현. 웹은 WebCrypto 우선, X25519·Ed25519가
  없으면 `@noble/curves`·`@noble/hashes`만 허용. 앱은 `cryptography` +
  `flutter_secure_storage`만 허용.

## 4. 메시지·키 형식 (버전 포함, 이후 버전 무시 규칙 적용)

- 1:1 암호문 본문: `{v:1, type:"msg", dh, n, pn(enc), ct}` (base64url).
  prekey 동봉형: `{v:1, type:"prekey", ik, ek, spk_id, opk_id?, ct}`.
- Sender Key 분배: 1:1 `ciphertext` 안에 `{v:1, type:"sk", chain, sign, gen}`.
- 그룹 암호문: `{v:1, type:"group", sender, gen, n, ct, sig}`.
- 첨부: 파일마다 무작위 256비트 키로 AES-256-GCM. 키·해시·이름은
  암호화 본문 안에, R2에는 암호문만. 썸네일도 같은 키로 암호화.
- 보안 코드: 양쪽 Ed25519 공개키 지문(SHA-256, 앞 60자리 숫자 20개씩
  3줄 + QR). 상대 기기·키 변경 시 방에 `security_notice` 발행.

## 5. 새 기기 기록 제공 (대표 결정)

- 방식: 복원 문구(8자 이상, 강도 표시) 기반 암호화 백업. 서버는
  암호문만 보관하고 문구를 모른다.
- 백업 내용: 신원키, 서명 prekey, sender key, 래칫 상태(체인·카운터·
  건너뛴 키 상한 200), 방별 복호화 기록(방당 최대 2000건·전체 20MB).
- 키 유도: PBKDF2-SHA256 10만 회 + 기기 무작위 salt → AES-256-GCM.
  다운로드는 인증 + 속도 제한. 복원 실패 사유는 구분하지 않는다.
- 복원: 새 기기 로그인 → 문구 입력 → 내려받아 복호화 → 키 설치·기록
  채움 → 내 다른 기기에 알림. 문구를 잊으면 복원 불가(새 키 발급,
  기존 백업은 요청 시 삭제). 문구 변경은 재암호화 후 교체.
- 한계: 백업 시점 이후 메시지는 새 기기에 없다가 이후 수신분부터
  보인다. 백업을 가진 자의 과거 해독 가능성은 2장의 절충을 따른다.

## 6. 키 수명·교체

- 서명 prekey 주 1회, 일회용 prekey 잔량 5개 미만이면 20개 보충.
- 기기 추가: 새 기기가 번들 등록 → 상대방이 다음 발신 때 자동 세션.
  방에 `security_notice`(기기 추가)를 남긴다.
- 기기 분실·로그아웃: 서버 기기 삭제 + 키 폐기 + 상대방 알림.
  웹 키는 IndexedDB 추출 불가 키로, 로그아웃 시 삭제.
- 탈퇴: 전 기기 키 삭제 + 백업 삭제 + 상대방 알림.
- 그룹 퇴장·내보내기: 남은 멤버 전원 sender key 교체(나간 자는 이후
  메시지 복호화 불가). 봇 초대: 평문 전환 확인 후 sender key 폐기.

## 7. 서버 강제 규칙 (E2 구현)

- E2EE 대상 방에서 `text`·`image`·`file` 등 평문 종류는 4xx로 거부하고
  `ciphertext`만 받는다. 봇·공식·오픈채팅 방은 예외.
- 남의 기기 키 등록·삭제는 403. 앱 최소 버전 미만은 업데이트 안내 후 차단.
- 키 변경·기기 변경 시 `security_notice` 발행 + 감사로그. E2EE 방의
  알림 본문·로그에 평문을 넣지 않는다.

## 8. 기존 기능 영향 (E8 구현)

- 알림: 서버는 "새 메시지"만, 내용은 기기가 복호화해 로컬 표시.
- 검색: E2EE 방은 기기 내 검색만. 링크 미리보기 기본 꺼짐.
- 번역·음성 인식: 사용자가 해당 메시지에 직접 요청할 때만, 매번 안내.
- 신고: 신고자가 기기에서 복호화해 동의 후 첨부.
- 내보내기: "이 기기의 대화 내보내기"를 웹·앱에 추가.
- 관리자: "내용 열람 불가, 신고 접수분만 검토" 표시.

## 9. 테스트 전략

- 공통 벡터 `scripts/fixtures/e2ee_vectors.json`: X3DH·래칫·sender key·
  백업의 고정 입출력. 웹(node --test)과 앱(flutter test)이 같은 벡터로
  통과해야 웹↔앱 상호 복호화를 인정한다.
- E2E: 웹→앱, 앱→웹, 2기기 동기화, 3인 그룹, 퇴장 후 복호화 불가,
  D1 평문 0건(행 직접 검사), R2 암호문 검사, 복원 왕복.
- E2EE 기능 플래그는 로컬·테스트에서만 켜고 실서버 반영 때 켠다.
